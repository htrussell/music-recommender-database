1. Executive summary

The system supports music discovery from a listener's natural-language request and optional public YouTube playlist. It uses a catalog-grounded recommendation flow: the API chooses a bounded catalog operation, retrieves candidates, and supplies approved context to a language model.

The proposed product goal is to turn a listener-reviewed playlist and stated intent into a useful, explainable queue. Listeners should be able to correct the taste summary, set hard exclusions, refine recommendations in conversation, and explicitly confirm any chat-inferred preference before it is saved. Primary users are listeners; the product owner is the proposed sponsor. Production streaming integration, audio playback, payments, advertising, and fully automated preference capture are outside the proposed demo scope. These are target business requirements, not current demo guarantees.

The guide draft describes a PostgreSQL catalog prototype, but the current code-grounded inventory is more specific: Parquet is the canonical catalog, DuckDB is the primary AI query engine, and PostgreSQL is the reloadable backup/fallback. The guide informs business scope; repository code/configuration determine implementation status.

Scope: catalog discovery, playlist import context, static catalog ETL, DuckDB query serving, a read-only streaming-habits demo-profile lookup, PostgreSQL backup/fallback, and proposed consent-led import/review, persistent profiles and explicitly saved queues, Kafka/Avro user events, short-lived conversation records, expiring pgvector-backed topic memories, privacy-minimized model telemetry, and analytic projections. The active queue remains session memory until explicit Save; PostgreSQL stores saved queue state and Kafka carries only asynchronous lifecycle events. Persistent chat history is off by default and requires separate opt-in. Durable user/context/event/telemetry infrastructure remains proposed; the demo profile is an opt-in static fixture, not an authenticated or persistent account.

The current demo imports public YouTube playlists with yt-dlp and accepts normalized playlist JSON. The guide's import-method decision concerns the future product and remains open. Generated queues are transient today; the target lets the listener explicitly save a chosen queue in PostgreSQL. Queue inputs are imported playlist context and stated/confirmed profile data, not presumed live playback events.

2. Architecture principles

Portable canonical layer

Keep transformed Parquet as the shared, rebuildable catalog snapshot.

Purpose-fit query engines

DuckDB reads columnar files directly; PostgreSQL supplies relational backup and fallback.

Constrained model access

Expose named tools and a validated SQL fallback, never direct model database credentials.

Lineage before automation

Retain source mapping, snapshot identity, and data-quality results with each build.

Consent and listener control

Require recorded, purpose-specific consent before import or persistence; support inspect, correct, clear, and delete controls.

Explainable, reviewed inputs

Queue reasons cite reviewed playlist rows, confirmed preferences, or catalog facts; unconfirmed AI inferences remain suggestions.

Session context by default

Keep chat history off by default; do not persist listener context without opt-in, retention, and access design.

Principles 1–3 are implemented. Lineage/quality reporting is partial. Consent, listener control, explainable input provenance, and opt-in chat persistence are target requirements, not implemented capabilities.

Store messages/summaries as searchable text and structured columns; JSONB is optional for bounded auxiliary metadata. Use pgvector only for compact topic memories, not every message; select dimensions from a versioned embedding model. The extension is not installed/configured in this project; verify availability and permissions before implementation. Start with exact search and user/expiry filters; benchmark before adding HNSW/IVFFlat. Neither schema belongs in the model-generated SQL allowlist.

6. Physical design and proof of concept

Canonical

Zstandard Parquet; portable compact snapshot; primary source for DuckDB and reload.

Primary query

DuckDB in-memory connection creates views with read_parquet; tool API is parameterized and bounded.

Backup / fallback

PostgreSQL 15 with relational PK/FK constraints; batch load is full refresh, not incremental.

User context · target

Separate PostgreSQL serving schemas for profiles, explicitly saved queues, and opt-in conversation/memory data; never include them in the catalog loader or model SQL allowlist.

Models

Demo: Cloudflare Worker for generation; Ollama is configured for embeddings only. Local generation or hybrid cloud/local serving is possible but not currently wired.

The DDL and loader are in load_postgres.py. The existing PoC contains the eight measured Parquet datasets. The PostgreSQL loader validates column order and streams in batches up to 10,000 rows.

Full logs have a short fixed retention; useful topics may remain longer but also have a hard maximum lifetime. At a configurable age/context-utility threshold, summarize only useful, non-sensitive topics; save the memory and minimal source-conversation IDs before purging messages. Retrieval ranks by semantic similarity adjusted by recency, confidence, and importance; only actually included memories update their last-retrieved time. Retrieval falloff is not deletion, and usage does not extend absolute expiry. Exact retention/decay thresholds are TBD. A deletion request removes source logs and derived memories/embeddings by default. No raw messages, summaries, or vectors go to Kafka/HDFS by default.

Use PostgreSQL for owner-scoped message retrieval and pgvector for compact memory summaries, not as an Avro blob store. JSONB is optional for auxiliary metadata only. Messages and memories remain in a separate serving schema/database from rebuildable catalog tables. A cloud summarization/generation call sends selected text outside the server, so apply the same minimization and provider-retention review as other model calls.

8. Master data

No master-data platform or golden-record workflow exists. Spotify track IDs are retained; artist, album, and genre integer IDs are generated per transform build and can shift when source membership changes. Source files remain upstream authority; the current Parquet build is local snapshot authority and PostgreSQL is derivative. Add a build ID and stable identity mapping before cross-build joins. The demo CSV's listener_id is sequential, not an authenticated account ID. Its 14 artist labels have unique normalized matches in this snapshot. Genre labels are ambiguous after normalization: several have multiple catalog IDs, while Afrobeats, Lo-fi, and R&B do not directly identify an active track-genre row. Use a curated, versioned genre-alias crosswalk before retrieval.

9. Metadata and lineage

Field mappings live in transform_erd.py, the loader's TABLE_PARQUET_MAP, and DuckDB's table list. Column order is validated. A source checksum, source date, transform version, snapshot ID, persisted row-count/quality report, and field-level lineage artifact are not yet maintained. Add a manifest with each immutable snapshot.

Target listener lineage connects each import batch and original row/provider ID to validation and catalog-match status, catalog snapshot, corrected-summary version, and recommendation reason. Retain only what is needed to explain a decision; owner-scope it and delete personal lineage with its source data.

10. Data quality

Current checks cover unique IDs, unique one-to-one tables, track-to-album completeness, and several reference-set relationships; PostgreSQL adds PK/FK enforcement, and loader validates expected columns/integer conversions. Risks include ambiguous title/artist matching, missing optional data, inconsistent aliases/tags, partial dates, and deterministic tie-break choices. There is no quarantine, reconciliation report, threshold policy, or ongoing quality dashboard.

Target import quality requires 100% row accounting: accept each row or show a duplicate, unsupported, incomplete, or ambiguous reason. Only reviewed rows may ground recommendations. Queue acceptance tests must verify all hard exclusions and per-item supporting evidence. These are unverified target tests, not current quality results.

11. Data governance

README lists Kaggle sources under MIT, CC-BY-SA-4.0, GPL-2.0, and CC0 terms. The repository's code license does not override obligations on a merged derived catalog. Review source terms before redistribution. MusicBrainz data is operator-supplied and needs separate terms review. Listener profiles and conversations are not persisted today; the target requires recorded, purpose-specific consent before playlist import or personal-data persistence. Persistent conversation history is off by default and requires separate opt-in. A 24-hour deletion target is proposed for the demo, but the test must cover user tables, saved queues, summaries/embeddings, caches, projections, logs, and backup expiry. Since the current target outbox FK cascades, hard deletion must not erase an unpublished deletion event; define a minimal tombstone/acknowledgment path before implementation. Full logs should expire on a short fixed window or after successful consolidation; topic memories also need a hard maximum age. Retrieval falloff alone is not deletion. Model telemetry must exclude raw prompts/responses, credentials, and unnecessary identity; set separate access and retention controls for metrics, traces, and archived invocation events. A generated queue becomes persistent only when the listener explicitly saves it.

12. Security and AI data contract

Models have no direct database connection. The API exposes named DuckDB operations and validates optional PostgreSQL SQL. In the demo, prompts, approved profile details, and selected catalog rows are sent to the configured Cloudflare Worker. A local-only deployment could run the API and a generation-capable local model beside DuckDB/Parquet and PostgreSQL, keeping this context on the operator's server; this is not currently wired. A hybrid deployment can route selected calls to cloud models. For proposed persistent context, the API must resolve the authenticated user before loading profile, conversation, or memory rows; never let the model select arbitrary listener IDs or issue direct SQL against these stores. Consent failure must block import/persistence; unconfirmed inferred preferences stay request-scoped; only reviewed rows and confirmed preferences may ground recommendation reasons.

14. Target state and scalability

For current static size, Parquet + DuckDB is intentionally lightweight. As data grows, add immutable versioned directories, build manifests, atomic publication, quality summaries, and AP-labeled DuckDB benchmarks before adding indexes/partitioning. Keep PostgreSQL rebuildable while it remains useful. Reassess managed storage if concurrency, update frequency, or availability requirements change.

The target listener flow is consent-led: every imported row has a reviewable outcome, recommendations explain their supporting evidence and respect hard exclusions, and chat-inferred preferences remain suggestions until confirmed. The active queue remains transient until the listener explicitly saves it to PostgreSQL; Kafka carries only lifecycle events. Persistent conversation history is off by default and requires separate opt-in. A 24-hour deletion target is not verified; event-projection deletion needs a minimal tombstone/acknowledgment path that is not lost to outbox cascade.

Proposed pgvector is only for topic-memory retrieval; it is not a catalog vector index. Durable profiles, Kafka/Avro user events, short-lived conversation storage, expiring topic memories, and model telemetry are specified targets, not current components. Select embedding dimensions and retention/decay thresholds before implementation, and test owner/expiry filters. Interaction analytics require consented event capture; the separate streaming-habits CSV is not a replacement for application events. Cloud serving has provider/network/cost/privacy constraints; local serving can limit external data transfer but requires capacity and operational support.

15. Roadmap, risks, and accepted tradeoffs

  1. Version snapshots; add source checksums, build manifest, and transformation metrics.
  2. Stage/validate new Parquet and publish atomically; replace destructive PostgreSQL reload with safe swap.
  3. Measure AP1–AP5 latency and recommendation match quality; add privacy-minimized model-call telemetry and freshness monitoring.
  4. Harden deployment: production secrets, authentication, rate limiting, provider review, and retention controls.
  5. Resolve consent purposes, target import method, chat opt-in/retention, and deletion semantics/tombstone acknowledgment; generated queues are explicitly saved by listener action.
  6. Build consent gates, reviewed row outcomes, owner-scoped profile and exclusions; verify row accounting and 24-hour deletion end to end.
  7. Add explainable queue reasons, hard-exclusion tests, listener confirmation before inferred preferences are saved, and measure the 100-track / <5 s / ≥95% target.
  8. Add Kafka/Avro, conversation/memory, telemetry, and analytics only after retention, provider-data, and access policies are approved; they remain unimplemented drafts.
