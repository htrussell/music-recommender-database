# Music Recommender Database

A local music-discovery demo backed by a Parquet music catalog. The browser UI
sends recommendation and catalog requests to a FastAPI service. DuckDB queries
the Parquet files directly; PostgreSQL is a separately loaded relational
backup and read-only fallback.

## Project overview

The current catalog path is:

```text
Kaggle CSV sources -> transform_erd.py -> transformed/*.parquet
                                      -> DuckDB catalog queries
                                      -> PostgreSQL backup / fallback
```

The browser UI is served by Nginx on port 8080. Its `/api` requests are
forwarded to the local FastAPI service. Text generation is delegated to the
configured Cloudflare Worker; Ollama runs locally for the configured
`nomic-embed-text:v1.5` embedding model. Docker Compose starts the services
needed by the demo. Hadoop, Kafka, Spark, and Jupyter are optional services
defined in the same Compose file.

| Path | Purpose |
| --- | --- |
| `index.html`, `app.js`, `styles.css` | Browser application |
| `backend/main.py` | FastAPI application, playlist import, AI orchestration, and PostgreSQL fallback |
| `backend/duckdb_service.py` | DuckDB catalog and demo-profile service |
| `backend/requirements.txt` | Pinned Python dependencies for the API and DuckDB services |
| `csv/` | Downloaded source CSVs (not committed) and the Kaggle download helper |
| `transform_erd.py` | Normalize source data and write the canonical Parquet tables |
| `transformed/` | Generated Parquet tables (not committed) |
| `load_postgres.py` | Load the Parquet snapshot into PostgreSQL |
| `docker-compose.yml` | Local app, database, and optional data-platform services |
| `reports/final/architecture.html` | Architecture blueprint with embedded ERDs |
| `reports/final/architecture.md` | Detailed text architecture blueprint |
| `reports/final/erd/` | Standalone catalog and proposed-schema ERDs |

## Setup and run

### Prerequisites

- Python 3.10 or newer (used by the data setup script).
- Docker Desktop or Docker Engine with Docker Compose v2; the engine must be running.
- Git Bash or WSL on Windows, or Bash on macOS/Linux.
- `curl` (used by the demo launcher to wait for the web UI).
- Kaggle API credentials to download source files. Existing CSV files can be
  reused instead; see [Setup options](#setup-options).

### System requirements

The base Docker demo is a lightweight local catalog application. The following
are practical resource estimates, not formal benchmark guarantees:

| Configuration | CPU | Docker memory | Project Docker volume disk |
|---|---|---|---|
| Minimum local demo | 2 CPU cores | 4 GB | 5-6 GB |
| Recommended local demo | 4 CPU cores | 6-8 GB | 5-6 GB |
| Full pgvector catalog build | 4+ CPU cores | 6-8 GB | 5-7 GB |

The minimum configuration can run the catalog, PostgreSQL, DuckDB, Ollama, and
the web/API containers. Docker Desktop memory should be allocated to the engine
before starting the demo.

For full semantic retrieval, the pgvector build adds roughly:

- 274 MB for the local `nomic-embed-text:v1.5` model
- About 275 MB for 768-dimensional float32 vector values for 89,741 tracks
- Roughly 300-600 MB for the PostgreSQL HNSW index
- Additional PostgreSQL pages and temporary build memory
- Approximately 2,800 Nomic embedding batches when embedding the full catalog
  with the default batch size

Reserve approximately 1-2 GB of additional project Docker volume disk for the pgvector vectors,
indexes, database pages, and build overhead. This is an estimate, not a measured
value; the actual requirement should be recorded after a full 89,741-track build.
The 5-6 GB project Docker volume estimate is based on the measured current
project volume usage of approximately 4.3 GB: Ollama 3.793 GB, PostgreSQL
0.478 GB, and the remaining project data volumes below 0.02 GB. The full
pgvector catalog build is estimated to add roughly 1-2 GB, so a 5-7 GB
project-volume reserve covers the current stack and the incremental build.
Docker memory of 6-8 GB is recommended during the first full embedding build;
CPU availability primarily determines build duration. The full build is not
required to run the base demo.

The catalog service defaults to four DuckDB threads and a 1 GB DuckDB memory
limit to reduce host resource pressure. These are DuckDB settings, not hard
limits on the container's total memory. Override `DUCKDB_THREADS` and
`DUCKDB_MEMORY_LIMIT` in the root `.env` if needed.
Large queries may spill to disk, run more slowly, or fail if the limit is too
small. Other local applications and models also use host memory; close unneeded
applications if the system is under memory pressure.
After changing these settings, recreate the catalog service with
`docker compose up --build -d duckdb`.

The local Nomic model performs embedding work, while Cloudflare Workers AI
provides text generation. The embedding build uses local Ollama CPU resources
and does not consume Cloudflare model neurons.

The setup and launcher scripts are intended to be run from the repository root.
They create/use `.venv` for the local data preparation tools and build the
application containers through Docker Compose.

### 1. Run unified setup

On Windows, Linux, or macOS:

```bash
python setup.py
```

The interactive launcher:

- asks whether to download Kaggle sources, reuse existing CSVs, or reuse existing Parquet files
- prompts for Kaggle username and a hidden API-key entry when credentials are missing
- optionally prompts for a YouTube Data API key and saves it in the local `.env`
- writes `~/.kaggle/kaggle.json` with user-only Unix permissions when needed
- creates `.venv` and installs data-loading dependencies
- transforms the catalog
- asks before replacing PostgreSQL music tables
- offers `none`, `subset`, or `full` pgvector embeddings
- optionally starts the web demo

Kaggle credentials may instead be supplied through `KAGGLE_USERNAME` and
`KAGGLE_KEY`, or an existing `~/.kaggle/kaggle.json`. Do not commit credentials.

#### Optional YouTube API key

The key is optional. With it, queue items can search for embeddable YouTube
videos and display a preview; without it, users can still follow the YouTube
search link. Existing playlist imports do not need a key.

To create a key, [create or select a Google Cloud project](https://console.cloud.google.com/),
enable the YouTube Data API v3 in its API Library, then create an API key on
the [Credentials page](https://console.cloud.google.com/apis/credentials).
Restrict the key to the YouTube Data API v3.

During interactive setup, choose to configure the optional key and enter it at
the hidden prompt. For non-interactive setup, create `.env` in the repository
root with `YOUTUBE_API_KEY=your-key`, or set `YOUTUBE_API_KEY` in the process
environment. Docker Compose passes the key to the backend; an environment
variable takes precedence over `.env`. Restart the demo after changing it.
The `.env` file is Git-ignored, but contains a secret: do not share or commit it.

Select the play button on a queue item to search YouTube on demand. The song and
artist are sent to YouTube. The app retrieves video lengths and compares them
with the catalog track length, allowing a difference of 30 seconds or 25% of
the track length, whichever is greater. Duration-compatible results are sent
to the configured Cloudflare Worker for a match. Only a high-confidence match
is selected automatically; otherwise, choices with their lengths appear when
the tab is focused. All search results remain available for manual selection,
including videos with a different or unavailable length. If the track or video
length cannot be checked, select a result manually. The extra video-details
request uses YouTube API quota. Choose another result if the match is
incorrect; playback is controlled by YouTube's visible embedded player. When a
video ends, the track is marked finished and the queue moves to the next track;
**Skip track** marks it skipped and advances. Progress is kept while the queue
is open and resets when a new queue is built. Browser autoplay restrictions or
an off-screen player can require pressing play for the next track. If a video
is unavailable or no match is found, choose another result, search on YouTube,
or skip; it is not marked finished automatically. YouTube API quota applies.
No key is sent to the browser or the matching model.

Automation examples:

```bash
python setup.py --download reuse-csv --skip-postgres-load --semantic none --non-interactive --yes
python setup.py --download download --semantic subset --embedding-limit 32 --start --yes
python setup.py --download reuse-parquet --semantic full --start --yes
```

The existing Bash entry point delegates to the unified launcher:

```bash
bash ./setup.sh
```

### 3. Start the demo

```bash
bash ./start.sh
```

The script builds and starts the frontend, AI API, DuckDB service, PostgreSQL,
and Ollama dependencies, waits for the UI, and opens a browser where supported.
Visit <http://localhost:8080> if the browser does not open automatically. The
first launch may take several minutes while Docker images and the Ollama
embedding model are downloaded. The launcher does not download source datasets
or generate Parquet files; run setup first unless the required data artifacts
already exist.

### Setup options

To reuse source CSVs already in `csv/` and skip Kaggle downloads:

```bash
bash ./setup.sh --skip-download
```

Keep these downloaded source files in `csv/` when reusing local data:
`dataset.csv`, `artists.csv`, `album_ratings.csv`, and
`music_streaming_habits_2026.csv`. The last file provides the demo profile
lookup.

To skip the confirmation before replacing the PostgreSQL music tables (for
example, in automation):

```bash
bash ./setup.sh --yes
```

The `--yes` option is destructive to the existing loaded music tables. It does
not delete the PostgreSQL volume, but the loader replaces those tables with the
current Parquet snapshot. Use `bash ./setup.sh --help` to see all options.

After setup, connect to the local PostgreSQL catalog with:

```bash
docker compose exec postgres psql -U airflow -d track-db
```

## How the demo works

The UI is served at <http://localhost:8080>. Catalog-backed recommendations
use the `gemma` model key on the Cloudflare Worker at
`https://music-rec-ai.htrussell.workers.dev`; chat and catalog/SQL planning use
the `granite` model key. If a model returns no message content or invalid JSON, the
API retries with the other configured model.
Queue generation searches the local catalog using goal terms, then asks `gemma`
to rank eligible catalog tracks. The goal takes precedence over playlist and
sample-profile taste signals. Up to two additional ranking attempts are made;
if needed, goal-term search results and then broader catalog tracks fill the
queue. Broader fallback tracks may not match the goal and are labeled in the
queue. Goal-term matches in genre and artist metadata are prioritized over
incidental words in titles. Ranking failures are reported alongside any catalog fallback.
On first opening a browser session, import and review a public YouTube playlist,
choose a synthetic listener ID (1–4,000), or skip setup. The selected playlist
or listener is saved for the session and restored after refresh. **Reset setup**
clears these settings, learned preferences, and the current queue without
clearing chat or recommendation history. Use **Personalize your queue** to change the playlist,
sample, or listener preferences later, and save changes for the session;
**Session details** beneath the queue contains the recommendation note and
checks. Imported tracks and the candidate catalog are available in their
expandable sections.
For a direct request such as “songs by my top artist,” the loaded sample's
top artist is used for catalog search and only tracks credited to that artist
are selected. Matching sample reference tracks are eligible, but playlist,
history, and explicit exclusions still apply. The queue may be shorter if the
initial search has insufficient matches. This does not apply to similar-artist
or general discovery goals.

The duration is a **minimum** calculated from catalog milliseconds. The final
whole track may exceed it. Tracks without a usable catalog duration are not
counted. If catalog search fails or there is insufficient eligible audio, a
partial queue is retained and the shortfall is reported. The recommendation
note includes candidate, exclusion, AI-ranking, and fallback counts.

Imported playlist tracks, sample-profile reference tracks (except as noted
above), explicit exclusions, and previously recommended tracks are excluded. Explicit exclusions are
case-insensitive text matches against available track, artist, and genre
metadata; concepts absent from that metadata cannot be reliably checked.
Use **Clear recommendation history** to allow previously recommended tracks
again without removing the playlist or sample profile.
Playlist, sample, and prior
tracks are checked by ID, artist/title identity, and normalized title. Within a
queue, only the first matching title is retained, regardless of artist. This
prevents alternate-artist covers with matching titles but can also omit
different songs that share a title. For YouTube imports, the filter also checks
parts of video titles such as `Artist - Song (Official Video)` and repeated
artist prefixes. For titles of at least eight characters, playlist and
sample-reference exclusions additionally allow one character edit, or two when
the longer title has at least twelve characters. Shorter titles require an exact
normalized match. These conservative checks can still exclude distinct songs
with similar titles and do not identify all covers.

The separate **Load Songs for Prompt** action verifies AI-proposed titles and
artist credits against the local catalog. It requires a credible artist and an
exact, recognized-version, or high-confidence title match; a matching artist
alone does not validate a different song.
Music chat uses the loaded sample profile for direct top-artist
questions and distinguishes it from the listener's real preferences. It can
recover some malformed model responses and retries when they cannot be read.
The API sets task-specific output-token limits to constrain generated response
size. Set `CLOUDFLARE_WORKER_URL` in the shell or Compose `.env` file to
override the Worker endpoint. `nomic-embed-text:v1.5` remains configured as the
local Ollama embedding model. For catalog questions, the API asks the Worker's
SQL model to select a bounded catalog tool.
Artist and track search, album search, and genre comparisons run as parameterized queries
against DuckDB, which queries the transformed Parquet files from
`transformed/` at startup without copying the catalog into DuckDB tables.
Artist lookup provides matching names, countries, popularity, and catalog tags
when available; the tags can be noisy and are not definitive genres. The lookup
cannot establish a listener's favorite artist or facts absent
from the catalog. Chat is instructed to acknowledge missing evidence rather than
guess, though model responses may still be inaccurate.
PostgreSQL is a separately loaded relational backup/query fallback, derived
from those same Parquet files. Prompts, approved profile details, and relevant
catalog rows are sent to the Cloudflare Worker for model processing. If the
model selects an unsupported catalog operation, or DuckDB is unavailable, the
API can fall back to its existing read-only PostgreSQL query path. PostgreSQL
fallback SQL is still validated against the music-table allowlist and row limit
and runs using the `music_reader` role.
`MUSIC_READER_PASSWORD` can be set in the shell or a Compose `.env` file to
override the local-development default.

The API health endpoint is <http://localhost:8080/healthz>. It checks the
PostgreSQL reader connection and reports local Ollama embedding availability
without making Ollama required for the base demo.
The DuckDB service has its own `/healthz` endpoint on the internal Compose
network; it is not published as a host port by default.

Playlist and taste-profile review/save remain browser-session data. A listener
profile is not written into the music database. Chat-inferred preferences stay
as suggestions until the listener confirms each one; only confirmed
preferences can influence recommendations or be saved in the browser session.
The demo can load one of the 4,000 sample profiles in
`csv/music_streaming_habits_2026.csv` by listener ID. DuckDB reads that file as
a separate, read-only profile view and identifies up to 40 catalog tracks
matched by top artist and curated top-genre aliases. These tracks are shown as
taste references and normally excluded from new queues; they are not actual listening
history. Top artist, top genre, top mood, and matching catalog examples may be
sent to the model; other sample attributes are shown locally. These synthetic
fixture IDs are not authenticated users or streaming event history. The selected
ID is retained only when the listener saves the browser-session profile.
Public YouTube playlist links are imported by the local backend using `yt-dlp`;
no third-party API key is required in the frontend. The AI can match alternate
title spellings and YouTube title variations against the read-only music
catalog. Normalized JSON playlist files can also be imported.

Prompts, approved profile details, and relevant catalog rows are sent to the
configured Cloudflare Worker for model processing. Do not send private or
sensitive information to the demo. The local-development credentials and
service configuration are not intended for production deployment.

## Data layout and architecture

`transform_erd.py` writes Zstandard-compressed Parquet as the canonical
transformed catalog. The original Kaggle downloads remain CSV source files.
The catalog snapshot consists of:

| Parquet file | Contents |
| --- | --- |
| `genre.parquet` | Normalized genre labels |
| `artists.parquet` | Catalog artist identities |
| `album.parquet` | Album details |
| `tracks.parquet` | Track details |
| `album_scores.parquet` | Album rating aggregates |
| `track_feel.parquet` | Audio features |
| `track_artists.parquet` | Track-to-artist bridge |
| `artist_genres.parquet` | Artist-to-genre bridge |

DuckDB reads these files directly; it does not copy the catalog into persistent
DuckDB tables. PostgreSQL is a separately loaded relational backup and
read-only fallback, not the canonical catalog source.

The PostgreSQL loader streams Parquet data in bounded batches, while DuckDB
reads those files directly. The optional
`scripts/export_musicbrainz_parquet.py` exports a compact recording/title/
artist-credit index from a separately imported MusicBrainz PostgreSQL database
to `musicbrainz/recordings.parquet`; it does not download or import the
MusicBrainz database. Set `MUSICBRAINZ_DSN` when running the exporter. The
export orders rows by normalized title so DuckDB can prune Parquet row groups
for exact-title lookups. The DuckDB verifier uses this index when present,
favoring exact artist credits and omitting ambiguous or unknown title matches.

The legacy `scripts/csv_to_parquet_hdfs.py` remains an optional HDFS export
path, reads the canonical Parquet tables, and expects a reachable
`namenode:9000`. Kafka is already in Compose, and Avro could be used for
versioned listener-feedback events if/when a schema registry and consumer are
added. Avro streaming should not replace Parquet for analytical catalog
storage.

For more detail, see the [architecture blueprint](reports/final/architecture.html),
its [Markdown version](reports/final/architecture.md), and the
[standalone ERD diagrams](reports/final/erd/).
The user-serving and conversation-memory diagrams describe proposed schemas;
they are not implemented or persisted by the current demo.

## Useful commands

Run these from the repository root in a Bash shell:

| Task | Command |
| --- | --- |
| Check running services | `docker compose ps` |
| Follow application logs | `docker compose logs -f frontend ai-api duckdb` |
| Follow PostgreSQL logs | `docker compose logs -f postgres` |
| Stop containers and network, retaining named data volumes | `docker compose down` |
| Start the demo again | `bash ./start.sh` |
| Apply changes to the AI API and catalog service | `docker compose up -d --no-deps --build ai-api duckdb` |
| Run backend unit tests in the running API container | `docker compose exec ai-api python -m unittest discover -s /app -p 'test_*.py'` |
| Run frontend recommendation regression tests (Node.js required) | `node --test tests/test_recommendations.js` |
| Open a PostgreSQL shell | `docker compose exec postgres psql -U airflow -d track-db` |

`docker compose down -v` also deletes named volumes, including PostgreSQL and
Ollama data. Use it only when you intentionally want to remove those local
databases and downloaded models.

The following additional services are defined in Compose but are not started
by `start.sh`: Hadoop/HDFS, ZooKeeper, Kafka, Spark, and Jupyter. Starting them
is optional and may consume substantial memory and disk space. When running,
their configured host ports include HDFS `9000`/`9870`, ZooKeeper `2181`,
Kafka `9092`/`29092`, Spark `7077`/`18080`/`18081`, and Jupyter `8888`/`14040`.

## Troubleshooting

- **Docker command fails or the launcher cannot connect:** start Docker
  Desktop/Engine, confirm `docker compose version` works, and retry.
- **Setup reports missing Kaggle credentials:** set both
  `KAGGLE_USERNAME` and `KAGGLE_KEY`, or install `kaggle.json` under
  `~/.kaggle/`. If source files are already present, use `--skip-download`.
- **Setup cannot find a source CSV:** verify the downloaded/existing files are
  in `csv/`; rerun without `--skip-download` if a required source is missing.
- **PostgreSQL tables are empty:** run setup to transform and load the catalog.
  Loading replaces the music tables and requires confirmation unless `--yes`
  is supplied.
- **The UI does not become ready:** inspect `docker compose ps` and
  `docker compose logs frontend ai-api duckdb ollama`. On first launch, allow
  time for image and embedding-model downloads. The API health check requires
  PostgreSQL and reports Ollama embedding availability separately; Ollama is
  optional for the base demo.
- **A host port is already in use:** stop the process using it or edit the
  corresponding port mapping in `docker-compose.yml` before starting Compose.

## Development and tests

The API and DuckDB service dependencies are pinned in
[`backend/requirements.txt`](backend/requirements.txt). The Docker image builds
install them automatically. To run backend unit tests, start the demo and run
the test command in [Useful commands](#useful-commands). The tests do not
download Kaggle datasets, but the API container must have been built.

Data preparation dependencies are installed into `.venv` by `setup.sh`. To
rebuild the Parquet snapshot from the CSVs without downloading them again, use
`bash ./setup.sh --skip-download`; note that the full setup also replaces the
loaded PostgreSQL music tables after confirmation.
