# Music Recommender Database

A local music-discovery demo backed by a Parquet music catalog. The browser UI
sends recommendation and catalog requests to a FastAPI service. DuckDB queries
the Parquet files directly; PostgreSQL is a separately loaded relational
backup and read-only fallback.

## Project overview

The current catalog path is:

```text
Kaggle CSV sources -> transform_erd.py -> transformed/*.parquet
                                      -> DuckDB catalog queries
                                      -> PostgreSQL backup / fallback
```

The browser UI is served by Nginx on port 8080. Its `/api` requests are
forwarded to the local FastAPI service. Text generation is delegated to the
configured Cloudflare Worker; Ollama runs locally for the configured
`nomic-embed-text:v1.5` embedding model. Docker Compose starts the services
needed by the demo. Hadoop, Kafka, Spark, and Jupyter are optional services
defined in the same Compose file.

| Path | Purpose |
| --- | --- |
| `index.html`, `app.js`, `styles.css` | Browser application |
| `backend/main.py` | FastAPI application, playlist import, AI orchestration, and PostgreSQL fallback |
| `backend/duckdb_service.py` | DuckDB catalog and demo-profile service |
| `backend/requirements.txt` | Pinned Python dependencies for the API and DuckDB services |
| `csv/` | Downloaded source CSVs (not committed) and the Kaggle download helper |
| `transform_erd.py` | Normalize source data and write the canonical Parquet tables |
| `transformed/` | Generated Parquet tables (not committed) |
| `load_postgres.py` | Load the Parquet snapshot into PostgreSQL |
| `docker-compose.yml` | Local app, database, and optional data-platform services |
| `reports/final/architecture.html` | Architecture blueprint with embedded ERDs |
| `reports/final/architecture.md` | Detailed text architecture blueprint |
| `reports/final/erd/` | Standalone catalog and proposed-schema ERDs |

## Setup and run

### Prerequisites

- Python 3.10 or newer (used by the data setup script).
- Docker Desktop or Docker Engine with Docker Compose v2; the engine must be running.
- Git Bash or WSL on Windows, or Bash on macOS/Linux.
- `curl` (used by the demo launcher to wait for the web UI).
- Kaggle API credentials to download source files. Existing CSV files can be
  reused instead; see [Setup options](#setup-options).

The setup and launcher scripts are intended to be run from the repository root.
They create/use `.venv` for the local data preparation tools and build the
application containers through Docker Compose.

### 1. Configure Kaggle credentials

Either set both environment variables in the shell that will run setup:

```bash
export KAGGLE_USERNAME="your-kaggle-username"
export KAGGLE_KEY="your-kaggle-api-key"
```

Or place the Kaggle API token in `~/.kaggle/kaggle.json` with permissions
restricted to your user. Do not commit credentials to the repository. On
Windows, the Bash home directory is used by the script.

### 2. Download, transform, and load the catalog

```bash
bash ./setup.sh
```

This creates `.venv`, installs the Kaggle and Parquet dependencies, downloads
the source CSVs into `csv/`, creates eight canonical Parquet files in
`transformed/`, starts PostgreSQL, and loads the Parquet data into its
relational tables. The loader drops and recreates the music tables. Setup asks
for confirmation before this database replacement; do not confirm if you need
to preserve tables in the local `track-db` database.

### 3. Start the demo

```bash
bash ./start.sh
```

The script builds and starts the frontend, AI API, DuckDB service, PostgreSQL,
and Ollama dependencies, waits for the UI, and opens a browser where supported.
Visit <http://localhost:8080> if the browser does not open automatically. The
first launch may take several minutes while Docker images and the Ollama
embedding model are downloaded. The launcher does not download source datasets
or generate Parquet files; run setup first unless the required data artifacts
already exist.

### Setup options

To reuse source CSVs already in `csv/` and skip Kaggle downloads:

```bash
bash ./setup.sh --skip-download
```

Keep these downloaded source files in `csv/` when reusing local data:
`dataset.csv`, `artists.csv`, `album_ratings.csv`, and
`music_streaming_habits_2026.csv`. The last file provides the demo profile
lookup.

To skip the confirmation before replacing the PostgreSQL music tables (for
example, in automation):

```bash
bash ./setup.sh --yes
```

The `--yes` option is destructive to the existing loaded music tables. It does
not delete the PostgreSQL volume, but the loader replaces those tables with the
current Parquet snapshot. Use `bash ./setup.sh --help` to see all options.

After setup, connect to the local PostgreSQL catalog with:

```bash
docker compose exec postgres psql -U airflow -d track-db
```

## How the demo works

The UI is served at <http://localhost:8080>. Catalog-backed recommendations
use the `llama` model key on the Cloudflare Worker at
`https://music-rec-ai.htrussell.workers.dev`; chat and catalog/SQL planning use
the `glm` model key. If a model returns no message content or invalid JSON, the
API retries with the other configured model.
Direct Prompt Mode uses `llama` to generate tracks. Playlist-grounded
recommendations use the imported playlist as taste context, exclude its tracks
from new queues, and skip a redundant catalog-planning call;
other catalog-backed requests continue to use DuckDB. Direct Prompt Mode
verifies titles and artist credits against the local catalog using exact matches
or lenient fuzzy title/artist similarity, and makes up to two additional
discovery passes to fill a short playlist. It prefers matching artist credits
but can select the closest title candidate when the model returns a mismatched
artist or several plausible matches; occasional catalog mismatches are possible.
Tracks already in an imported playlist and tracks recommended previously in the
browser session are excluded from new queues.
It never exceeds the requested duration. A partial queue is retained if a refill
request fails or the catalog has too few matching tracks.
The API sets task-specific output-token limits to constrain generated response
size. Set `CLOUDFLARE_WORKER_URL` in the shell or Compose `.env` file to
override the Worker endpoint. `nomic-embed-text:v1.5` remains configured as the
local Ollama embedding model. For catalog questions, the API asks the Worker's
SQL model to select a bounded catalog tool.
Track search, album search, and genre comparisons run as parameterized queries
against DuckDB, which queries the transformed Parquet files from
`transformed/` at startup without copying the catalog into DuckDB tables.
PostgreSQL is a separately loaded relational backup/query fallback, derived
from those same Parquet files. Prompts, approved profile details, and relevant
catalog rows are sent to the Cloudflare Worker for model processing. If the
model selects an unsupported catalog operation, or DuckDB is unavailable, the
API can fall back to its existing read-only PostgreSQL query path. PostgreSQL
fallback SQL is still validated against the music-table allowlist and row limit
and runs using the `music_reader` role.
`MUSIC_READER_PASSWORD` can be set in the shell or a Compose `.env` file to
override the local-development default.

The API health endpoint is <http://localhost:8080/healthz>. It checks the
PostgreSQL reader connection and the configured local Ollama embedding model.
The DuckDB service has its own `/healthz` endpoint on the internal Compose
network; it is not published as a host port by default.

Playlist and taste-profile review/save remain browser-session data. A listener
profile is not written into the music database. Chat-inferred preferences stay
as suggestions until the listener confirms each one; only confirmed
preferences can influence recommendations or be saved in the browser session.
The demo can load one of the 4,000 sample profiles in
`csv/music_streaming_habits_2026.csv` by listener ID. DuckDB reads that file as
a separate, read-only profile view and adds up to 40 catalog tracks matched by
top artist and curated top-genre aliases to the candidate pool. Only top artist,
top genre, and top mood are sent to the model; other sample attributes are shown
locally. These synthetic fixture IDs are not authenticated users or streaming
event history. The selected ID is retained only when the listener saves the
browser-session profile.
Public YouTube playlist links are imported by the local backend using `yt-dlp`;
no third-party API key is required in the frontend. The AI can match alternate
title spellings and YouTube title variations against the read-only music
catalog. Normalized JSON playlist files can also be imported.

Prompts, approved profile details, and relevant catalog rows are sent to the
configured Cloudflare Worker for model processing. Do not send private or
sensitive information to the demo. The local-development credentials and
service configuration are not intended for production deployment.

## Data layout and architecture

`transform_erd.py` writes Zstandard-compressed Parquet as the canonical
transformed catalog. The original Kaggle downloads remain CSV source files.
The catalog snapshot consists of:

| Parquet file | Contents |
| --- | --- |
| `genre.parquet` | Normalized genre labels |
| `artists.parquet` | Catalog artist identities |
| `album.parquet` | Album details |
| `tracks.parquet` | Track details |
| `album_scores.parquet` | Album rating aggregates |
| `track_feel.parquet` | Audio features |
| `track_artists.parquet` | Track-to-artist bridge |
| `artist_genres.parquet` | Artist-to-genre bridge |

DuckDB reads these files directly; it does not copy the catalog into persistent
DuckDB tables. PostgreSQL is a separately loaded relational backup and
read-only fallback, not the canonical catalog source.

The PostgreSQL loader streams Parquet data in bounded batches, while DuckDB
reads those files directly. The optional
`scripts/export_musicbrainz_parquet.py` exports a compact recording/title/
artist-credit index from a separately imported MusicBrainz PostgreSQL database
to `musicbrainz/recordings.parquet`; it does not download or import the
MusicBrainz database. Set `MUSICBRAINZ_DSN` when running the exporter. The
export orders rows by normalized title so DuckDB can prune Parquet row groups
for exact-title lookups. The DuckDB verifier uses this index when present,
favoring exact artist credits and omitting ambiguous or unknown title matches.

The legacy `scripts/csv_to_parquet_hdfs.py` remains an optional HDFS export
path, reads the canonical Parquet tables, and expects a reachable
`namenode:9000`. Kafka is already in Compose, and Avro could be used for
versioned listener-feedback events if/when a schema registry and consumer are
added. Avro streaming should not replace Parquet for analytical catalog
storage.

For more detail, see the [architecture blueprint](reports/final/architecture.html),
its [Markdown version](reports/final/architecture.md), and the
[standalone ERD diagrams](reports/final/erd/).
The user-serving and conversation-memory diagrams describe proposed schemas;
they are not implemented or persisted by the current demo.

## Useful commands

Run these from the repository root in a Bash shell:

| Task | Command |
| --- | --- |
| Check running services | `docker compose ps` |
| Follow application logs | `docker compose logs -f frontend ai-api duckdb` |
| Follow PostgreSQL logs | `docker compose logs -f postgres` |
| Stop containers and network, retaining named data volumes | `docker compose down` |
| Start the demo again | `bash ./start.sh` |
| Run backend unit tests in the running API container | `docker compose exec ai-api python -m unittest discover -s /app -p 'test_*.py'` |
| Open a PostgreSQL shell | `docker compose exec postgres psql -U airflow -d track-db` |

`docker compose down -v` also deletes named volumes, including PostgreSQL and
Ollama data. Use it only when you intentionally want to remove those local
databases and downloaded models.

The following additional services are defined in Compose but are not started
by `start.sh`: Hadoop/HDFS, ZooKeeper, Kafka, Spark, and Jupyter. Starting them
is optional and may consume substantial memory and disk space. When running,
their configured host ports include HDFS `9000`/`9870`, ZooKeeper `2181`,
Kafka `9092`/`29092`, Spark `7077`/`18080`/`18081`, and Jupyter `8888`/`14040`.

## Troubleshooting

- **Docker command fails or the launcher cannot connect:** start Docker
  Desktop/Engine, confirm `docker compose version` works, and retry.
- **Setup reports missing Kaggle credentials:** set both
  `KAGGLE_USERNAME` and `KAGGLE_KEY`, or install `kaggle.json` under
  `~/.kaggle/`. If source files are already present, use `--skip-download`.
- **Setup cannot find a source CSV:** verify the downloaded/existing files are
  in `csv/`; rerun without `--skip-download` if a required source is missing.
- **PostgreSQL tables are empty:** run setup to transform and load the catalog.
  Loading replaces the music tables and requires confirmation unless `--yes`
  is supplied.
- **The UI does not become ready:** inspect `docker compose ps` and
  `docker compose logs frontend ai-api duckdb ollama`. On first launch, allow
  time for image and embedding-model downloads. The API health check requires
  PostgreSQL and Ollama with the configured embedding model to be ready.
- **A host port is already in use:** stop the process using it or edit the
  corresponding port mapping in `docker-compose.yml` before starting Compose.

## Development and tests

The API and DuckDB service dependencies are pinned in
[`backend/requirements.txt`](backend/requirements.txt). The Docker image builds
install them automatically. To run backend unit tests, start the demo and run
the test command in [Useful commands](#useful-commands). The tests do not
download Kaggle datasets, but the API container must have been built.

Data preparation dependencies are installed into `.venv` by `setup.sh`. To
rebuild the Parquet snapshot from the CSVs without downloading them again, use
`bash ./setup.sh --skip-download`; note that the full setup also replaces the
loaded PostgreSQL music tables after confirmation.
